## 2026-05-21. Шаг: стабилизация auth / participant / RSVP flow в appwrite mode

### Цель

Закрепить первый multi-user сценарий после реального backend-теста: Appwrite session -> profile -> participant -> RSVP, без изменения визуального интерфейса.

### Что сделано

1. В `authService` усилено восстановление пользователя в `VITE_DATA_MODE=appwrite`:
   - если Appwrite session уже существует, она переиспользуется;
   - новый anonymous guest не создается без явного действия пользователя;
   - если у существующего Appwrite account отсутствует документ в `profiles`, он восстанавливается для того же `userId`.
2. В `createGuestUser()` сохранена модель “reuse existing session first”:
   - новый anonymous session создается только если текущей Appwrite session нет;
   - profile для guest-пользователя теперь создается или восстанавливается гарантированно при нормальном backend-сценарии.
3. В `App.vue` закреплена продуктовая модель:
   - `participant` = пользователь вошел в приватный контекст события;
   - `RSVP` = отдельный ответ на приглашение;
   - RSVP со статусом “не пойду” не удаляет participant.
4. Добавлена защита от ложного участника:
   - в appwrite mode `ensureCurrentParticipant()` больше не создает participant для runtime demo-user;
   - сначала должен существовать реальный `currentUser`, а уже затем создается participant.
5. В `eventService` скорректирован список `Мои события` для appwrite mode:
   - теперь home строится только по связанным событиям;
   - пользователь видит только события, где он organizer или participant;
   - чужие несвязанные события больше не попадают в домашний список.
6. Из MVP убрано начисление очков за RSVP-переключения:
   - повторное переключение RSVP больше не позволяет фармить points;
   - lightweight-геймификация через points за загрузку фото сохранена.
7. Исправлен invite-link flow после входа:
   - `pendingInviteCode` не теряется во время auth gate;
   - найденное событие сначала добавляется в реактивный `homeEvents`, а затем открывается;
   - participant создается только после восстановления реального `currentUser/profile`;
   - после успешного join список `Мои события` обновляется повторно, и приглашенное событие начинает отображаться как связанное.

### Что важно по архитектуре

- `participant` не равен RSVP и не должен удаляться при отказе от участия;
- invite-link flow теперь осознанно работает как:
  `session -> profile -> open event -> participant -> RSVP`;
- событие может появляться в “Мои события” после открытия invite link, потому что после входа пользователь становится participant этого события;
- профиль и participant теперь жестче связаны в appwrite flow, чтобы не возникал сценарий “participant есть, profile нет”.

### Как проверить вручную

1. Включить `VITE_DATA_MODE=appwrite`.
2. Открыть приложение в одном браузере и создать событие.
3. Скопировать invite link.
4. Открыть invite link во втором браузере или в режиме инкогнито.
5. Войти как гость.
6. Проверить в Appwrite Console:
   - есть Appwrite session;
   - есть документ в `profiles` для того же `userId`;
   - есть `participant` для пары `eventId + userId`.
7. Переключить RSVP несколько раз и убедиться, что points у participant не растут от каждого изменения статуса.
8. Вернуться на Home и проверить, что отображаются только связанные события.

```bash
npm run build
```

## 2026-05-21. Шаг: починка shared event visuals, organizer display и edit flow в appwrite mode

### Цель

Исправить три связанные проблемы после первого реального shared-event сценария:
- у гостя background не должен подменяться cover-изображением;
- имя организатора должно приходить из `participants`, а не отображаться как `userId`;
- редактирование события в appwrite mode должно открывать текущую форму и после сохранения показывать обновлённое событие без ручной перезагрузки.

### Что сделано

1. В `eventService` исправлено восстановление visual state из Appwrite:
   - `coverStart` и `backgroundStart` теперь поднимаются по разным цепочкам;
   - `backgroundFileId` больше не падает в `coverStart` как fallback;
   - если background-файл отсутствует, событие использует отдельный background fallback, а не обложку.
2. В `participantService` добавлен helper получения организатора события:
   - сначала ищется participant по паре `eventId + organizerId`;
   - если прямой записи нет, используется fallback на participant с ролью `organizer`.
3. В `eventService` добавлено async-обогащение события именем организатора:
   - `organizerName` не возвращается в `events` schema;
   - display name организатора подтягивается через `participants`;
   - если organizer participant найден, UI получает его `displayName` и инициалы.
4. В `App.vue` усилен create/edit flow:
   - после `createEvent()` и `updateEvent()` organizer participant фиксируется до финального обновления экрана;
   - затем событие перечитывается через `eventService.getEventById(...)`;
   - refreshed event сразу попадает в `homeEvents` и открывается как актуальный `selectedEvent`.
5. Это сохраняет текущий визуальный интерфейс, но делает shared event state стабильнее между браузерами.

### Что важно по архитектуре

- `organizerName` по-прежнему не хранится в `events`, чтобы не плодить денормализацию;
- shared visual truth теперь разделяет:
  - `coverFileId` -> poster/cover;
  - `backgroundFileId` -> event background;
- edit flow в appwrite mode теперь больше опирается на повторное чтение backend-данных, а не только на локальный optimistic-объект.

### Проверка

```bash
npm run build
```

## 2026-05-17. Шаг 1: старт frontend-прототипа главного окна

### Цель

Создать первый рабочий frontend-прототип главной страницы дипломного проекта Event Gallery. Интерфейс должен использовать Partiful только как UX-референс: простая главная, крупный hero-блок, заметная кнопка создания события, карточки и легкое праздничное настроение.

Важно: бренд, тексты, изображения, логотипы, конкретные стили и исходный код Partiful не копировались. Внешние изображения и API изображений не использовались.

### Что было изучено

В папке `приеры страниц partiful/main` лежит сохраненная главная страница Partiful. Она оказалась экспортом Framer с большим количеством автогенерированного CSS, JS и внешних ссылок. Поэтому ее код не переносился в проект.

Из референса взята только общая UX-логика:

- верхняя навигация;
- крупный первый экран;
- основная кнопка создания события;
- визуальные карточки события;
- ощущение простоты и праздника;
- легкая динамика без сложных анимаций.

### Архитектурное решение

Для frontend выбран стек из концепции диплома:

- Vue 3 для компонентного интерфейса;
- Vite для dev-сервера и сборки;
- TypeScript для типизации;
- CSS без внешних изображений и тяжелых animation-библиотек.

На этом шаге Tailwind CSS пока не подключался, чтобы быстрее получить понятный первый прототип и не усложнять стартовую структуру. Его можно добавить позже, если будет удобнее развивать дизайн через utility-классы.

### Созданные файлы

- `package.json` - описание npm-проекта, зависимости и команды запуска.
- `package-lock.json` - зафиксированные версии npm-зависимостей.
- `index.html` - HTML-точка входа Vite-приложения.
- `vite.config.ts` - конфигурация Vite с Vue-плагином.
- `tsconfig.json` - настройки TypeScript.
- `src/main.ts` - создание Vue-приложения и подключение стилей.
- `src/App.vue` - главный экран, переключение тем и модальное окно входа.
- `src/style.css` - вся визуальная система первого прототипа.
- `src/env.d.ts` - типы Vite.
- `.gitignore` - исключение `node_modules`, `dist` и служебных файлов.

### Что реализовано

Главная страница содержит:

- бренд `Event Gallery`;
- верхнюю навигацию;
- hero-блок с описанием проекта;
- кнопку `Создать событие`;
- кнопку `Войти по коду`;
- декоративную карточку события;
- mock QR-блок;
- mock-photo карточки без внешних изображений;
- блок основного сценария: создать событие, пригласить гостей, собрать фото;
- блок кастомности события;
- переключение тем: `Вечер`, `Студенты`, `Квест`;
- блок ключевых возможностей MVP;
- модальное окно авторизации;
- два режима входа: гостевой вход и вход в профиль.

### Почему так сделано

Для дипломного MVP важно показать идею быстро и надежно:

- главный экран сразу объясняет назначение системы;
- кнопка создания события видна в первом экране;
- гостевой вход снижает сложность авторизации;
- темы события демонстрируют кастомность без сложного редактора;
- mock-photo и CSS-градиенты заменяют реальные изображения до подключения хранилища;
- визуальные бейджи и очки заранее готовят основу для геймификации.

## Шаг 12 — 2026-05-20

### Цель

Подготовить MVP-авторизацию и модель участия в событиях через отдельные сервисы, не меняя визуальный дизайн и не подключая Appwrite раньше времени.

### Что добавлено

1. Новые типы:
   - `src/types/user.ts` — глобальный пользователь приложения (`CurrentUser`);
   - `src/types/participant.ts` — участие пользователя в конкретном событии (`EventParticipant`).
2. Новый сервис `src/services/authService.ts`.
3. Новый сервис `src/services/participantService.ts`.
4. В тип события добавлено поле `organizerId?: string`, чтобы связать событие с пользователем по `userId`, а не только по имени.

### Как сейчас работает authService

- `getCurrentUser()` читает пользователя из `localStorage`;
- `createGuestUser()` создает или переиспользует гостя и сохраняет его локально;
- `requestEmailCode(email)` в demo-режиме сохраняет мок-код;
- `verifyEmailCode(email, code)` принимает код `000000` как успешный;
- `upgradeGuestToProfile(email, code)` сохраняет тот же `userId`, но переводит пользователя из `guest` в `profile`;
- `logout()` очищает текущего пользователя из `localStorage`.

Это важно для архитектуры: после апгрейда гостя до профиля его `userId` не меняется, значит позже не потеряются события, достижения, фото и связи с участием.

### Как сейчас работает participantService

- участники событий хранятся отдельно от самих событий;
- ключ `localStorage`: `event-gallery:participants`;
- участие привязывается к паре `eventId + userId`;
- повторный вход в событие не создает дубликат участника;
- при создании события текущий пользователь автоматически добавляется как `organizer`.

### Что изменено в App.vue

1. Убран захардкоженный пользователь как источник правды.
2. При старте интерфейс загружает `currentUser` через `authService`.
3. Если пользователь отсутствует, автоматически создается demo-гость, чтобы текущий UI не ломался.
4. Создание и обновление события теперь может связывать событие с `currentUser.id`.
5. После создания или обновления события вызывается `participantService`, чтобы зафиксировать организатора как участника события.
6. Текущая модалка авторизации сохранена по структуре, но теперь работает на `guest/email-code` логике вместо заглушки.

### Что пока НЕ подключено

- Appwrite Auth;
- Appwrite Database;
- реальные email-письма и SMTP;
- OAuth и Google-вход;
- email/password авторизация.

### Следующий шаг

Следующий разумный шаг — вынести пользовательский профиль, RSVP и действия внутри страницы события на реальные `userId`/`participantId`, а затем подменить `authService` и `participantService` с `localStorage` на Appwrite.
