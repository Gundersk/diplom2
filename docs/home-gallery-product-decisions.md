# Решения по Home, галерее, оплате и достижениям

Дата: 2026-05-18

Этот документ уточняет продуктовую логику после обсуждения Home-экрана, личной галереи, альбомов событий, оплаты и достижений. Он дополняет `docs/interface-reference-notes.md`.

## 1. Общая логика после авторизации

После успешной авторизации пользователь попадает не на длинный лендинг, а на Home-экран, похожий по роли на `welcome` в Partiful.

На Home должны быть:

- карточки событий пользователя;
- текущие, будущие и прошедшие события;
- события, где пользователь был участником;
- события, которые пользователь организует;
- кнопка создания нового события;
- иконка профиля;
- минимальное меню профиля;
- плашка уведомлений;
- встроенная личная галерея.

Что не делаем:

- встроенные личные сообщения как отдельный мессенджер;
- публичную афишу событий;
- сложные социальные рекомендации;
- отдельные кнопки `сделать публичным` / `сделать приватным`.

## 2. Профиль и уведомления

Иконка профиля должна открывать компактное меню.

Минимальные настройки профиля:

- изменить имя;
- изменить аватар;
- выйти из профиля.

Плашка уведомлений нужна для событийных уведомлений:

- объявление организатора в событии;
- ответ в чате события;
- новое фото в событии;
- полученное достижение;
- изменение статуса приглашения.

Для MVP уведомления можно сделать на mock-данных без реальной push-инфраструктуры.

## 3. Приватность событий

Для MVP все события считаются закрытыми.

Доступ:

- по ссылке;
- по QR-коду;
- через приглашение.

Не нужно добавлять публичный/приватный переключатель.

Настройка для организатора:

- приглашенные могут приглашать других;
- приглашенные не могут приглашать других.

Это лучше оформить как простой переключатель в настройках события: `Гости могут приглашать других`.

## 4. Home + галерея как единый гибридный экран

Личную галерею не нужно уводить в полностью отдельный экран на первом этапе. Лучше сделать гибрид:

- на Home события идут последовательно карточками;
- каждая карточка события выглядит как визуальная карточка мероприятия;
- карточка содержит фон/обложку события;
- в карточке есть основные данные события;
- в карточке есть медальки достижений;
- карточку можно раскрыть;
- при раскрытии появляются фото, которые пользователь сохранил из общего альбома этого события.

Основная идея: пользователь видит не просто сетку фотографий, а историю событий, где фото остаются визуально привязанными к конкретному мероприятию.

## 5. Режимы просмотра галереи

Нужны два режима:

1. Режим событий.
   - Основной режим.
   - Показывает карточки событий.
   - Каждую карточку можно раскрыть до фотографий.

2. Режим всех фото.
   - Включается кнопкой `Раскрыть все фото`.
   - Все события раскрываются.
   - Галерея становится похожа на обычную фотоленту.
   - При этом фото все равно остаются обернутыми в визуальные группы событий.

Важное требование: даже в режиме всех фото должно быть понятно, к какому событию относится каждая группа снимков.

## 6. Просмотр отдельной фотографии

Если пользователь открывает фото:

- фотография показывается крупно;
- по бокам или на фоне используется фон события;
- важные кнопки и текст должны быть поверх фонового слоя;
- при переходе к следующей фотографии из того же события фон остается прежним;
- при переходе к фотографии из следующего события фон меняется на фон нового события.

Это создает эффект последовательной фотогалереи, но сохраняет событийный контекст.

Правило слоев:

- фон события - нижний слой;
- декоративные элементы - средний или нижний слой;
- фото, навигация, кнопки, подписи - верхний слой.

## 7. Общий альбом события и личное сохранение

У каждого события есть общий альбом.

В общий альбом попадают:

- фото, загруженные напрямую;
- фото, отправленные в чат события.

Пользователь может сохранить фото из общего альбома в свою личную галерею.

Важно: в MVP можно считать, что фото физически не копируется. В личной галерее хранится связь:

- пользователь;
- событие;
- фото из общего альбома;
- дата сохранения;
- избранное или нет.

Если пользователь позже вернулся на страницу события и сохранил еще фото, они добавляются в уже существующую карточку этого события на Home.

## 8. Оплата / сбор денег

В приложении не должно быть реальных переводов.

Приложение:

- не переводит деньги;
- не проверяет факт перевода;
- не подключается к банкам;
- не хранит платежные данные;
- не является платежной системой.

Организатор может только указать:

- событие платное или нужно скинуться;
- сумму с человека;
- куда переводить: номер телефона, банк, комментарий или текстовая инструкция.

Участник может вручную нажать:

- `Оплатил`;
- `Оплачу позже`.

Для организатора можно показать простую статистику:

- сколько отметили `Оплатил`;
- сколько выбрали `Оплачу позже`;
- кто еще не отметил статус.

Это чисто визуальная и организационная функция.

## 9. Достижения для MVP

Достижений не должно быть слишком много.

В MVP нужны:

1. Автоматические достижения.
   - Работают как личные достижения участника.
   - Их можно включить или отключить при создании события.
   - Они присваиваются системой по простым правилам.

2. Кастомные личные достижения.
   - Создаются организатором.
   - Вручаются конкретному гостю.

3. Кастомные групповые достижения.
   - Создаются организатором.
   - Вручаются всему событию.

Визуальное разделение автоматических и личных достижений делать не нужно. Для пользователя они выглядят как личные медальки.

Групповые достижения показываются отдельно, выше или отдельной строкой.

## 10. Примеры автоматических достижений

Нейтральные примеры для диплома:

- `Первый кадр` - участник первым загрузил фото в альбом.
- `Папарацци` - участник загрузил больше всех фото.
- `Любимец альбома` - фото участника собрало больше всех лайков.
- `Коллекционер моментов` - участник сохранил 10 фото в личную галерею.
- `Активный гость` - участник оставил комментарий и загрузил фото.
- `Фото вечера` - одно из фото участника стало самым популярным.

Эти достижения закрывают требование геймификации без сложной игровой экономики.

## 11. Кастомные достижения

Для кастомного достижения нужны поля:

- название;
- описание;
- тип: личное или групповое;
- иконка из набора;
- цвет или стиль медальки;
- кому вручено.

Загрузка своей картинки для медальки может быть перспективой развития. Для MVP достаточно набора готовых иконок/эмодзи/простых CSS-медалей.

## 12. Как это влияет на следующие экраны

Следующий логичный шаг разработки:

1. Сделать Home после авторизации.
2. На Home показать:
   - верхнюю панель;
   - профиль;
   - уведомления;
   - кнопку создания события;
   - вкладки событий;
   - гибридную галерею карточек событий.
3. Добавить mock-данные событий, фото, достижений и уведомлений.
4. Реализовать раскрытие карточки события.
5. Реализовать кнопку `Раскрыть все фото`.

Это даст понятную основу для дальнейших экранов: создания события, страницы события и общего альбома.

## 13. UI-заметки

- Карточки событий должны быть спокойнее и минималистичнее, чем в альтернативном HTML-примере.
- Не использовать внешние Unsplash-картинки из примера.
- Для временных фото использовать CSS-градиенты, mock-photo блоки или локальные заглушки.
- Достижения лучше показывать отдельными маленькими медальками.
- Групповые достижения показывать отдельно от личных.
- Важные кнопки всегда должны быть выше декоративного слоя.
- На мобильных экранах карточки событий должны быть ровными, без наклонов и тяжелой декоративности.
